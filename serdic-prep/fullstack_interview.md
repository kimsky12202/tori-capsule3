## A. 풀스택 / 웹 기본

**A1. 본인이 만든 풀스택 프로젝트를 설명해주세요. (거의 무조건 나옴)**
> 토리 타임캡슐이라는 위치기반 타임캡슐 앱을 풀스택으로 만들었습니다. **프론트는 Flutter**(앱 UI, 지도, AR), **백엔드는 Go + PocketBase**로 직접 REST API(로그인·회원가입·캡슐·친구·챌린지·푸시)를 작성했고, **DB 스키마는 마이그레이션으로 관리**, **Docker Compose로 컨테이너화**, **Nginx 리버스 프록시 + Let's Encrypt TLS**로 배포까지 했습니다.
> 💡 "기획부터 배포·운영까지 한 사이클을 혼자 돌려봤고, 그래서 '서비스가 현장에서 돌아간다'는 게 무슨 의미인지 압니다." ← 공고 문구와 정확히 연결.

**A2. 프론트엔드와 백엔드를 함께 이해한다는 게 왜 중요한가요?**
> API 하나를 바꿔도 양쪽이 같이 움직여야 하기 때문입니다. 응답 형태(JSON 구조), 에러 처리, 인증 토큰 흐름, 실시간 연결을 양쪽 관점에서 보면 불필요한 왕복을 줄이고 장애 지점을 빨리 찾습니다. 토리에서 앱과 Go API의 계약(contract)을 직접 맞춰본 경험이 있습니다.

**A3. REST API를 설계할 때 무엇을 신경 쓰나요?**
> 자원 중심 URL, HTTP 메서드 의미(GET 안전·멱등, POST 생성 등), 적절한 상태코드, 일관된 에러 포맷, 인증/인가, 페이지네이션, 버전 관리입니다. 토리에서 `/login`, `/capsules` 같은 라우트를 Go로 직접 짜며 이 원칙을 적용했습니다.

## B. 실시간 통신 (WebSocket) ★ 공고 강조

**B1. ⭐ REST와 WebSocket의 차이는?**
> REST는 클라이언트가 요청해야 서버가 응답하는 **단발성 요청-응답**입니다. WebSocket은 한 번 연결을 맺으면 **양방향으로 계속** 메시지를 주고받습니다. 대시보드처럼 "서버에 새 이벤트가 생기면 즉시 화면에 떠야" 하는 경우, REST 폴링은 낭비가 크고 지연이 있어 WebSocket이 적합합니다.

**B2. SSE(Server-Sent Events)와 WebSocket은 언제 각각 쓰나요?**
> 서버→클라 **단방향** 푸시만 필요하면 SSE가 간단합니다(HTTP 기반, 자동 재연결). 클라→서버도 자주 보내야 하면(채팅, 제어 명령) **양방향**인 WebSocket입니다. 관제 대시보드가 "보기만" 하면 SSE로 충분하고, 사용자가 카메라를 제어하거나 명령을 보내면 WebSocket이 낫습니다.

**B3. ⭐ WebSocket 서버가 클라이언트 수천 개를 감당하려면?**
> ① 연결당 메모리·고루틴 관리(Go라면 연결마다 goroutine + 채널), ② 서버를 여러 대로 **수평 확장**하면 "어느 서버에 누가 붙었는지" 문제가 생기는데, 이때 **Redis pub/sub**으로 서버 간 메시지를 공유합니다. ③ 백프레셔(느린 클라이언트가 전체를 막지 않게 버퍼/드롭 정책), ④ 하트비트(ping/pong)로 죽은 연결 정리.

**B4. 연결이 끊기면 어떻게 처리하나요?**
> 클라이언트는 지수 백오프로 재연결, 서버는 ping/pong 타임아웃으로 죽은 연결 정리. 놓친 이벤트가 중요하면 "마지막 받은 ID 이후를 다시 달라"는 식의 **재동기화(catch-up)** 를 둡니다. (CCTV 이벤트라면 유실이 곤란하니 메시지 큐와 결합.)

## C. 데이터베이스 (PostgreSQL) ★ 공고 명시

**C1. ⭐ SQLite와 PostgreSQL의 차이, 언제 무엇을?**
> SQLite는 단일 파일·임베디드라 가볍고 개발·소규모에 좋지만 **동시 쓰기**에 약합니다. PostgreSQL은 서버형이라 다중 동시접속·트랜잭션·복제·확장에 강해 **산업용 운영**에 적합합니다. 토리는 PocketBase(SQLite)로 빠르게 만들었지만, 트래픽이 커지면 PostgreSQL로 옮기는 게 맞다고 봅니다. (그래서 직접 이전 실습도 했습니다.)

**C2. 인덱스가 뭐고 언제 쓰나요?**
> 자주 검색·정렬하는 컬럼에 인덱스(B-tree)를 두면 풀스캔 대신 빠르게 찾습니다. 단 쓰기 비용·저장공간이 늘어나니 무분별하면 안 됩니다. `EXPLAIN ANALYZE`로 실제 쿼리 계획을 보고 판단합니다.

**C3. 트랜잭션과 ACID는?**
> 여러 작업을 "모두 성공 아니면 모두 취소"로 묶는 게 트랜잭션이고, 원자성·일관성·격리성·지속성(ACID)을 보장합니다. 예: 캡슐 생성 + 멤버 등록이 한 트랜잭션 안에서 일어나야 중간 실패 시 데이터가 깨지지 않습니다.

**C4. 센서/시계열 데이터를 저장한다면? (회사 도메인)**
> 시간순으로 대량 적재되는 데이터라, PostgreSQL이면 **시간 기준 파티셔닝**이나 **TimescaleDB** 확장을 고려합니다. 오래된 원본은 다운샘플링·아카이브하고, 대시보드는 집계 테이블을 읽게 해 부하를 낮춥니다.

## D. Docker / 배포 / 운영 ★ 공고 명시

**D1. Docker를 왜 쓰나요?**
> "내 컴에선 됐는데" 문제를 없애려고요. 앱과 의존성을 이미지로 묶어 어디서나 같게 실행합니다. 토리도 PocketBase를 Dockerfile로 빌드하고 docker-compose로 띄웠습니다.

**D2. docker-compose는 무엇에 쓰나요?**
> 여러 컨테이너(백엔드·DB·Redis·프론트)를 한 파일로 정의해 한 번에 띄웁니다. 통합 데모에서 영상서비스+백엔드+PostgreSQL+Redis+대시보드를 compose로 한 번에 올릴 계획입니다.

**D3. 온프레미스와 클라우드를 함께 고려한다는 건? (Hybrid SaaS)**
> 공장 데이터는 보안·망분리 때문에 외부로 못 내보내는 경우가 많습니다. 그래서 **현장(온프레미스)에 엣지 서버**를 두고 영상분석 같은 무거운/민감한 처리를 현장에서 하고, **요약·메타데이터만 클라우드 SaaS**로 올려 통합 관제하는 구조가 됩니다. 컨테이너로 같은 이미지를 양쪽에 배포할 수 있다는 게 Docker의 장점이고요.

**D4. CI/CD가 뭐고 왜 필요한가요? (우대)**
> 코드 push → 자동 테스트 → 빌드 → 배포로 이어지는 자동화입니다. 수동 배포의 실수를 줄이고, 자주·안전하게 릴리스합니다. GitHub Actions로 토리에 붙여볼 계획입니다.

## E. 캐시 / 메시지 큐 (Redis, MQ) ★ 우대

**E1. Redis는 어디에 쓰나요?**
> 인메모리라 매우 빨라 ① 캐시(자주 읽는 데이터·세션), ② 실시간 **pub/sub**(WebSocket 서버 간 브로드캐스트), ③ 카운터·랭킹 등에 씁니다.

**E2. 메시지 큐는 왜 필요한가요? Redis pub/sub과 뭐가 다른가요?**
> 메시지 큐(RabbitMQ/Kafka)는 생산자와 소비자를 **분리**하고, 소비자가 느리거나 죽어도 메시지를 **쌓아두고 재시도**해 유실을 막습니다. Redis pub/sub은 "지금 듣고 있는" 구독자에게만 전달(놓치면 끝)이라 가볍지만 보장이 약합니다. **CCTV 이벤트처럼 유실되면 안 되는 대량 데이터는 메시지 큐**, 단순 실시간 브로드캐스트는 Redis가 적합합니다.

**E3. 영상 이벤트가 폭주하면(피크 트래픽) 어떻게?**
> 큐로 **버퍼링**해 백엔드가 자기 속도로 소비(소비자 수평 확장), 중요도 낮은 이벤트는 샘플링/드롭, DB엔 배치로 적재. "쏟아지는 입력 ↔ 처리 속도"를 큐가 완충합니다.

## F. Vision AI 기초 ★ 우대 (차별화 1순위)

**F1. RTSP가 뭔가요?**
> CCTV·IP카메라가 영상 스트림을 전송할 때 쓰는 표준 프로토콜입니다. OpenCV에서 `cv2.VideoCapture("rtsp://...")`로 받아 프레임 단위로 처리할 수 있습니다.

**F2. 영상에서 객체를 탐지하는 흐름은?**
> 프레임을 읽어 → 전처리(리사이즈/정규화) → 사전학습 모델(YOLO 등)로 추론 → 박스·클래스·신뢰도 결과 → 후처리(NMS) → 필요한 이벤트만(예: 안전모 미착용) 추려 백엔드로 전송. 직접 학습보다 **추론 파이프라인 구성**이 실무 핵심입니다.

**F3. DeepStream / TensorRT는? (키워드만 알아도 가점)**
> TensorRT는 NVIDIA GPU에서 추론을 최적화·가속하는 라이브러리, DeepStream은 **다중 카메라 영상 파이프라인**을 GPU에서 효율적으로 돌리는 SDK입니다. CCTV 수십~수백 대를 실시간 처리하려면 이런 가속이 필요합니다. (저는 OpenCV+YOLO로 원리를 익혔고, 확장 시 이 스택을 학습할 계획입니다.)

**F4. 영상 처리는 무거운데 실시간을 어떻게 보장하나요?**
> ① 매 프레임 말고 **N프레임마다** 추론(프레임 스킵), ② 해상도 다운스케일, ③ GPU 배치 추론, ④ 무거운 분석은 엣지에서, 결과만 전송, ⑤ 추론과 전송을 분리(큐). "정확도 vs 지연 vs 비용" 트레이드오프를 상황에 맞게 잡습니다.

## G. 시스템 설계 (단골 면접)

**G1. ⭐ "CCTV 100대 영상을 실시간 분석해 웹 대시보드에 보여주는 시스템"을 설계해보세요.**
> 단계로 답합니다:
> 1. **수집**: 각 현장 엣지 서버가 RTSP로 카메라 영상 수신.
> 2. **분석**: 엣지에서 Vision 추론(프레임 스킵·GPU). 영상 원본은 현장에 두고 **이벤트(JSON)만** 생성.
> 3. **전달**: 이벤트를 메시지 큐로 클라우드에 전송(유실 방지·버퍼링).
> 4. **저장/가공**: 백엔드가 큐를 소비해 PostgreSQL에 저장, 집계.
> 5. **실시간 표시**: 새 이벤트를 WebSocket(서버 간 Redis pub/sub)으로 대시보드에 푸시.
> 6. **확장**: 백엔드/WS 서버 수평 확장, LB, DB 읽기 복제, 캐시.
> 💡 "원본 영상은 안 올리고 이벤트만 올린다"는 대역폭·보안 포인트를 짚으면 도메인 이해도가 드러남.

**G2. 수평 확장 vs 수직 확장?**
> 수직은 한 서버를 더 좋게(CPU/RAM↑), 한계·단일장애점 있음. 수평은 서버를 늘림(상태 공유·LB 필요)으로 무한 확장에 가깝지만 복잡도↑. 실시간 서비스는 보통 수평 확장 + Redis로 상태 공유.

**G3. 장애가 나도 서비스가 죽지 않게 하려면?**
> 단일장애점 제거(다중화), 헬스체크+자동 재시작, 큐로 비동기 결합(한 부분이 죽어도 메시지 보존), graceful degradation(영상분석이 죽어도 대시보드는 마지막 상태 유지), 모니터링·알림.

**G4. 모니터링/로깅은 어떻게? (공고: 로그·이벤트·알림·모니터링)**
> 구조화 로그(JSON) 수집, 메트릭(요청수·지연·에러율·큐 적체) 수집해 대시보드(예: Prometheus+Grafana), 임계 초과 시 알림. "운영 가능한 서비스"의 필수 요소이고 공고가 명시한 부분입니다.

## H. 빠른 학습력 / 신기술 (회사가 본 부분)

**H1. 새로운 기술을 어떻게 빨리 익히나요?**
> 가장 작은 단위로 **직접 만들어 봅니다**. 가우시안 스플래팅도 라이브러리 없이 2D부터 밑바닥으로 구현해 원리를 잡았습니다. 문서를 읽고 끝내는 게 아니라 동작하는 데모로 만들어 한계까지 부딪쳐 봐야 진짜 이해라고 생각합니다.

**H2. 가우시안 스플래팅을 우리 디지털 트윈에 어떻게?**
> (→ `../gs-from-scratch/interview_prep.md` Q20~22 참고) 현장을 촬영해 포토리얼 3D 트윈을 만들고, 명시적·실시간 특성 덕에 웹에서 띄워 센서·AI 이벤트를 좌표에 올립니다. 정밀 계측엔 메시/LiDAR와 병행하는 하이브리드가 현실적입니다.

## I. 인성 / 지원동기

**I1. 왜 세르딕인가요?**
> "현실 산업 현장을 웹 실시간 3D로 옮기고 AI로 안전·효율을 높인다"는 방향이, 제가 풀스택으로 서비스를 끝까지 만들어본 경험과 가우시안 스플래팅을 직접 구현하며 느낀 매력이 만나는 지점이라서입니다. 신기술을 실제 산업 문제에 적용하는 회사라는 점이 끌렸습니다.

**I2. 신입인데 3년 경력 요건은? (정면돌파)**
> 연차 대신 **결과물로** 보여드리겠습니다. 혼자 풀스택 서비스를 기획·개발·배포·운영까지 했고, 공고를 보고 회사가 만드는 파이프라인(영상→AI→실시간 대시보드)을 축소판으로 직접 구현해봤습니다. "준하는 실력"을 코드로 증명하는 게 제 방식입니다.
